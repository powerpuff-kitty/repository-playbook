# Avoid duplicated truth

Give different material different homes: tutorials for a first success, how-to guides for tasks, reference for contracts, and architecture decisions for trade-offs. The README should route readers into these paths instead of repeating every detail.

Assign an authoritative location for version policy, environment support, generated counts and public API boundaries. Link to it from other documents. When information must appear in several places, generate it or test its consistency. Avoid manually maintained counts in both badges and tables.

Write claims with an evidence level. Implemented code, passing tests, reproduced benchmarks and upstream documentation are different sources of confidence. Record exact environments for measurements, and leave unmeasured fields unknown rather than borrowing numbers from unrelated hardware.

Review navigation and claims after refactors, scope changes and releases. Add a troubleshooting entry when repeated support questions reveal a missing assumption. Check commands from a fresh consumer perspective rather than only from a maintainer's configured machine.

The playbook does not automatically assess prose truthfulness. Its manual checks prompt reviewers to identify the claim, locate the supporting evidence and record any mismatch. A polished diagram or an authoritative tone is not evidence.
