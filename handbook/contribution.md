# Make participation practical

Contribution instructions should explain local setup, validation commands, the kinds of changes welcome, and how review works. Give issue forms enough structure to collect reproducible information without demanding irrelevant fields for documentation corrections.

Use a short pull-request template covering purpose, evidence and risk. Separate a rule proposal from a false-positive report: one changes policy, the other challenges an observation or detector. Maintainers should be able to reproduce a finding without asking for secret tokens or an entire private repository.

Ownership should match the team. A solo project can state one maintainer and an expected review path; it need not create artificial committees. A larger project can document area ownership and escalation. A CODEOWNERS file alone is not proof that owner review is enforced.

GitHub can supply community-health defaults through an owner's public `.github` repository. Therefore local absence of a contribution, conduct or security file is not automatically a failure. The offline auditor reports unknown until effective defaults are observed. A present file only passes a presence check: review whether the instructions and contact routes are actually usable.

Avoid aggressive stale-issue automation that closes unresolved reports simply because maintainers have not responded. Prefer explicit triage decisions with reasons.
