# Start with an observable problem

Pick one repository and one intended audience. Decide whether its primary deliverable is documentation, a catalogue, a library or an application. A hybrid project can be inspected with more than one profile; do not average their results into a universal score.

Read the README as someone who has never opened the project. Can they identify its purpose, requirements and the next action? Then run the offline audit from a separate playbook checkout. Save reports outside the target so the audit does not consume its own outputs on the next run.

Review failures first, especially incomplete first-use instructions and missing authoritative material. Next resolve unknown settings with dated evidence, and manually examine claims that cannot be inferred from filenames. Record exceptions with a reason, owner and review date; suppressing a warning without explaining it loses the useful part of the audit.

Start with one change that can be verified: a corrected command sequence, a broken link repaired, or a required check enforced. Re-run the relevant checks after the change. Keep findings attached to a revision or text digest. Do not compare two reports as if they inspected the same scope when profiles, exclusions or rule versions differ.

The baseline profiles intentionally do not require a public chat room, deployment or package release for every project. Larger teams and regulated projects need additional policies. The current CLI does not implement custom exceptions or maturity overlays; document those judgements in the accompanying review.

## Basis and references

These are playbook recommendations, not universal platform requirements. [Primary reference](https://docs.github.com/en/repositories/creating-and-managing-repositories/best-practices-for-repositories). See the rule catalogue for applicability and verification limits.
