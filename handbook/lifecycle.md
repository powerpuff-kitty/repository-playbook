# Document what maintainers actually support

State whether the project is experimental, actively maintained, in maintenance mode, deprecated or archived. Define what those words mean for releases, support and compatibility instead of using them as decorative labels.

A stable tool may need few commits. A busy repository may still have an unusable release. Evaluate maintenance through documented support, unresolved risks and working distribution rather than a simple last-commit threshold.

When deprecating or archiving, explain the reason, the last supported version, migration options and where historical documentation remains available. Preserve reproducibility information for existing users. Do not delete useful evidence to make the project appear cleaner.

Record ownership transfer and operational dependencies before handover. Identify accounts, deployment settings and package rights that are outside the repository without committing secrets. The playbook's initial roadmap explicitly separates implemented tools from future GitHub integrations and automatic remediation.
